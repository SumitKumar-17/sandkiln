---
title: Wire protocol
description: vsock, a length-prefixed JSON frame, and a client that doesn't reach for a full HTTP stack.
---

Host and guest talk over vsock — a channel Firecracker exposes directly, so the guest agent is reachable without any guest network configuration and without sharing an attack surface with the sandbox's own outbound networking. On the wire, every message is a 4-byte little-endian length prefix followed by that many bytes of JSON, not a newline-delimited stream — `exec` output can contain arbitrary bytes, including embedded newlines, and a length prefix is the one framing scheme a payload can't corrupt by accident. JSON itself is a deliberate, boring choice: dependency-light, readable in a log or packet capture while debugging, and a tagged `cmd`/`status` enum on both ends keeps the handful of request and response shapes honest without needing a schema compiler for a protocol this small.

Firecracker's own control surface is a related problem with a different shape. The host configures boot-source, drives, machine-config, and vsock at boot, and later pauses, snapshots, and resumes a VM, all through a fixed, small set of JSON PUT/PATCH requests over Firecracker's own Unix socket. Pulling in a full HTTP client crate for that buys nothing — none of chunked encoding, redirects, TLS, or connection pooling will ever be exercised against a socket that speaks exactly one fixed API. So the VMM crate hand-rolls the roughly ninety lines a minimal HTTP/1.1 client actually needs: write the request line, headers, and body; read the status line; read headers looking only for `Content-Length`; read exactly that many body bytes. It has its own unit tests, no async runtime dependency, and works cleanly from the blocking contexts — a background thread, a synchronous pause-then-snapshot sequence — it's actually called from.
