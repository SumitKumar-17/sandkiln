---
title: Persistence model
description: Sandbox vs. session, and why a snapshot points at paths instead of carrying values.
---

A sandbox is meant to be a persistent identity: a name, a config, filesystem state that outlives any one run. A session is one live microVM instance of it — a sandbox resumed daily for a week is one sandbox and seven sessions. The `Sandbox` type itself still doesn't make that distinction at the type level — it dies with its VM, same as when this was first written. What actually shipped instead: a caller-given `name` carried across the sandbox↔snapshot boundary (see [Named sandboxes & persistent stop](../../concepts/named-sandboxes/)), so the *identity* persists across stop/resume cycles even though the underlying type doesn't formally separate "identity" from "one running instance." That's a real, working answer to the caller-facing problem, arrived at without the type-level split this essay originally expected would be a prerequisite — worth knowing if you're reading the code expecting to find that split and won't.

A snapshot is not a self-contained artifact. It writes a memory file and a device-state file, and both record the rootfs drive by its *host path*, not its contents — the backing file itself is never copied into the snapshot. Resume later at the same path and it works. Delete that file, move it, or let a different sandbox's rootfs land at the same path in between, and resume boots a VM whose device state expects one filesystem while a different one is actually sitting there — silent corruption, not a clean error, because nothing in the snapshot format can tell the difference.

Networking has the same shape, more subtly. A VM's guest-visible IP and MAC are finalized via kernel boot arguments at the *original* boot and are frozen into the snapshotted memory image — they're guest-OS state the host has no way to reach or rewrite afterward. So whatever host tap device carries the same name the VM had at snapshot time is what the resumed guest keeps sending packets to, whether or not anything is still listening on it. Firecracker's snapshot-load API can rename the host side of that interface, but it can't change what the guest believes its own address is — so handing a resumed sandbox a fresh lease's tap device instead of its original one leaves the guest talking to a device nothing forwards for, with no error to show for it. That's why the resume path deliberately takes no network configuration of its own: the daemon holds onto the sandbox's original lease across a snapshot instead of releasing it, and hands that exact one back on resume. The vsock socket path is the one thing safe to regenerate fresh every time, because it's purely host-side plumbing the guest OS never sees or depends on.
