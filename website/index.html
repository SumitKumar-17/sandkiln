Why a microVM

      
Containers share a kernel. Sandboxes can't afford to.

      
Running code you didn't write — agent output, user uploads, third-party scripts — next to your own systems is a bad idea if the isolation boundary is a namespace. A compromised container can still be a compromised kernel. A compromised microVM is a compromised microVM.

Feature surface

      
Everything a sandbox platform needs. Built honestly.

      
Every card below is marked by what's actually true today — proven on real hardware — versus what's designed and queued. Nothing here is vaporware dressed as a feature.

Under the hood

      
Four crates. No crate reaches into another's internals.

      
The core is a Rust workspace, kept deliberately modular — the daemon can change without touching the guest agent, and the guest agent ships as its own 700KB static binary independent of everything that talks to it.

    


    

      

        
01

        
sandkiln-protocol

        
The wire format shared by host and guest — length-prefixed JSON, kept dependency-light so neither side reaches into the other.

      

      

        
02

        
sandkiln-guest-agent

        
Runs inside the microVM as a systemd service. Listens on vsock, answers exec / read / write / list — 700KB, static, musl.

      

      

        
03

        
sandkiln-vmm

        
Drives Firecracker directly: boot, network leasing, the vsock client. A hand-rolled HTTP client talks to Firecracker's API socket.

      

      

        
04

        
sandkiln-daemon

        
axum + tokio HTTP API wrapping the lifecycle — create, exec, list, stop — with auth, tags, and tracing built in from day one.

      

    


    

      
Boot lifecycle

      
What happens inside 33 milliseconds

    

    

      
01
Lease
A tap device and IP are leased from the pool, attached to the bridge.

      
02
Boot
Firecracker starts, boot-source/drive/machine-config/vsock are configured over its API socket.

      
03
Agent up
The guest kernel boots, systemd starts the guest agent, it binds its vsock port.

      
04
Ready
The host's vsock client connects — the sandbox can now run anything you send it.

      What the numbers actually say: create's mean was 369ms in the first measurement — far above the 33ms boot figure, because the ~300MB rootfs copy ran serially after the network lease. Parallelizing the two dropped it to 211ms, measured again, not assumed. The remaining gap is real file-copy time on this box's ext4 (no copy-on-write); a CoW-capable filesystem or a device-mapper layer is the next lever, not the boot path, which was already fast.
    

  






  

    

      
SDK

      
Four methods. That's the whole surface, on purpose.

      
The daemon's HTTP API is the source of truth — the SDK is a thin, fully-typed client over it, nothing more.

    


    
import { Sandbox } from "sandkiln";

// Boots a real Firecracker microVM — ~33ms, own kernel, own network.
const sandbox = await Sandbox.create({
  tags: { env: "ci", owner: "pipeline" },
});

const result = await sandbox.runCommand("python3", ["analyze.py"]);
console.log(result.stdout, result.exitCode);

const running = await Sandbox.list();
// → [{ id, createdAt, tags: { env: "ci", owner: "pipeline" } }]

await sandbox.stop(); // tap, IP, and rootfs copy are all released
