---
title: Persistence model
description: Sandbox vs. session, and why a snapshot points at paths instead of carrying values.
---

A sandbox is meant to be a persistent identity: a name, a config, filesystem state that outlives any one run. A session is one live microVM instance of it, so a sandbox resumed daily for a week is one sandbox and seven sessions. The `Sandbox` type itself still doesn't make that distinction at the type level; it dies with its VM, same as when this was first written. What actually shipped instead is a caller-given `name` carried across the sandbox↔snapshot boundary (see [Named sandboxes & persistent stop](../../concepts/named-sandboxes/)), so the *identity* persists across stop/resume cycles even though the underlying type doesn't formally separate "identity" from "one running instance." That's a real, working answer to the caller-facing problem, arrived at without the type-level split this essay originally expected would be a prerequisite. Worth knowing if you're reading the code expecting to find that split and won't.

A snapshot is not a self-contained artifact. It writes a memory file and a device-state file, and both record the rootfs drive by its *host path*, not its contents; the backing file itself is never copied into the snapshot. Resume later at the same path and it works. Delete that file, move it, or let a different sandbox's rootfs land at the same path in between, and resume boots a VM whose device state expects one filesystem while a different one is actually sitting there — silent corruption, not a clean error, because nothing in the snapshot format can tell the difference.

Networking has the same shape, more subtly. A VM's guest-visible IP and MAC are finalized via kernel boot arguments at the *original* boot and are frozen into the snapshotted memory image. They're guest-OS state the host has no way to reach or rewrite afterward. So whatever host tap device carries the same name the VM had at snapshot time is what the resumed guest keeps sending packets to, whether or not anything is still listening on it. Firecracker's snapshot-load API can rename the host side of that interface, but it can't change what the guest believes its own address is, so handing a resumed sandbox a fresh lease's tap device instead of its original one leaves the guest talking to a device nothing forwards for, with no error to show for it. That's why the resume path deliberately takes no network configuration of its own: the daemon holds onto the sandbox's original lease across a snapshot instead of releasing it, and hands that exact one back on resume. The vsock socket path is the one thing safe to regenerate fresh every time, because it's purely host-side plumbing the guest OS never sees or depends on.

## A fork violated this essay's own rule, and it took building time-travel restore to notice

`POST /snapshots/:id/fork` (see [Snapshots, resume, and fork](../../concepts/snapshots/)) boots a second live sandbox from a snapshot without consuming it. From day one, that forked sandbox shared the snapshot's rootfs *file* directly: not a copy, the literal same path. For as long as fork and its source snapshot were never both resumed/re-forked into two live things at once, this looked safe, because `Snapshot::forked_into` already refuses a second concurrent descendant.

But "concurrent" isn't the only way to violate the rule stated above. A *sequential* violation works too, and this essay already explains why: fork the snapshot, let the fork mutate the shared rootfs file, stop the fork, then resume (not fork) the *original* snapshot directly. Its device state still describes the rootfs as it was before the fork ever ran; the file on disk now has the fork's changes layered on top. Same failure mode as "delete that file, move it, or let a different sandbox's rootfs land at the same path" above, just reached by mutation instead of relocation.

This was reproduced live while building time-travel restore (below), not found by re-reading this essay first: write a marker file, fork, overwrite the marker in the fork, stop the fork, resume the original directly, and the marker comes back with the fork's value, not the original's. The fix follows directly from the rule already stated here: a fork now gets its own private rootfs clone (`cp --reflink=auto`, the same call `POST /sandboxes` already uses for a fresh boot) instead of the source snapshot's file. Once cloned, nothing about a fork's own writes can ever reach back into what the snapshot's next resume will see.

## Time-travel restore: keeping the checkpoint instead of deleting it

Resume's contract above ("consumes the snapshot, the record and its on-disk files are gone afterward") has a real cost nothing before this needed to weigh: once you resume, that exact save point is gone forever, even if all you wanted was to try something else from the same starting state. `POST /snapshots/:id/resume` still consumes the snapshot *record* the same way (a second resume of the same id still 404s), but by default now retires the underlying checkpoint into `GET /snapshots/history` instead of deleting it. From there it is restorable again later via `POST /snapshots/history/:id/restore`, as many times as wanted, and reclaimable outright via `DELETE /snapshots/history/:id`. `?retain_history=false` on resume opts back into the original, fully-destructive behavior.

Making retention safe needed the same rootfs-cloning fix as the fork bug above, for the identical reason: the *new* live sandbox resume produces gets its own private rootfs clone, never the checkpoint's original file, so anything that sandbox does afterward can never retroactively corrupt the checkpoint it came from. Restoring an old checkpoint mirrors this back: it clones the checkpoint's rootfs fresh for the newly-restored sandbox too, so the checkpoint itself stays pristine and restorable again.

The network-identity constraint from above still applies, generalized: restoring refuses (`409`, naming the current holder) while anything else sharing that checkpoint's frozen tap device/IP/MAC is currently live or held. That's the same one-live-descendant-at-a-time rule `forked_into` already enforces for fork, just extended across a whole lineage's history instead of only its single most recent snapshot. This is deliberately sequential, not branching: restoring an old checkpoint doesn't destroy or invalidate whatever came after it (those stay in history too), but two checkpoints from the same lineage can never both be live at once. True parallel branching would need a way to change a running guest's own network identity post-hoc, which needs in-guest cooperation this project's guest agent doesn't have, the same open problem that already rules out true concurrent forking.

A restored sandbox is not fork-shaped, though: it owns its network lease and rootfs outright (a freshly reserved lease, a private clone), so unlike a fork it stays snapshottable afterward. Restoring a checkpoint and then continuing forward from it starts a genuinely new branch of history, not a dead end.

Retaining every resume's checkpoint by default has a real, unbounded disk cost that's worth stating plainly: a full guest-memory dump plus a private rootfs copy, per checkpoint, forever, until deleted. Routine manual verification while building this feature alone filled a 468GB disk. `DELETE /snapshots/history/:id` exists specifically because of that finding, not as part of the original design. There's no automatic expiry yet, so a workload that resumes often and doesn't need to travel back further than its latest state should either delete old checkpoints itself or pass `?retain_history=false`.
