[Self-hosting quickstart](/getting-started/self-hosting) runs everything below with `scripts/setup.sh`. Read this page if you want to understand what each step does, need to customize something the flags do not cover, or are debugging a step that failed. Everything here corresponds to a real script, binary or setting in the repository.

Run `scripts/preflight-check.sh` at any point to see where you stand against everything below. It reads the same `SANDKILN_*` environment variables and defaults the daemon uses, so it tells you what is missing before you try to start anything.

## Prerequisites

- **Linux, x86_64.** The Firecracker guests and the prebuilt kernel and rootfs tooling target x86_64. Nothing here has been built or verified for aarch64.
- **`/dev/kvm`, readable and writable by the user who will run the daemon.** Bare metal and a VM with nested virtualization both work, because Firecracker only needs KVM. Check with `ls -la /dev/kvm`. If your user is not in the group that owns it, run `sudo usermod -aG kvm $USER` and log in again.
- **Root or `sudo` for one-time host setup only.** The daemon itself never runs as root. See [Capabilities](#capabilities).
- **Rust (stable, via `rustup`)** to build `core/`, plus the `x86_64-unknown-linux-musl` target and the `musl-tools` package to build the guest agent: `rustup target add x86_64-unknown-linux-musl`, and on Debian or Ubuntu `sudo apt install musl-tools`.
- **`debootstrap`, `ubuntu-keyring` and standard build tooling**, only if you build a production rootfs rather than use the small test image. Debian or Ubuntu: `sudo apt install debootstrap ubuntu-keyring`.
- **Disk.** Several GiB free for a production image build (the universal image defaults to 6GiB). The test image path needs under 500MiB.
- **Node.js 22.18+**, only to build the CLI or SDK from source instead of installing the published `sandkiln` and `sandkiln-cli` packages.

## Build, Firecracker and kernel

```bash
git clone https://github.com/SumitKumar-17/sandkiln.git
cd sandkiln/core
cargo build --release --workspace
```

This builds `sandkilnd` (at `core/target/release/sandkilnd`) and the `sandkiln-vmm` and `sandkiln-protocol` libraries it depends on. It does **not** build the guest agent, which is cross-compiled separately for the guest's musl target ([next section](#base-image-and-guest-agent)).

Install Firecracker and the jailer:

```bash
scripts/host-setup/install-firecracker.sh ~/sandkiln-tools
```

This downloads both into `~/sandkiln-tools/bin`. Pin a release other than the script's default with `FIRECRACKER_VERSION=v1.16.1 scripts/host-setup/install-firecracker.sh ~/sandkiln-tools`.

You also need a guest kernel. The quickest source is Firecracker's public CI artifacts:

```bash
images/fetch-test-image.sh ~/sandkiln-tools/images
```

This fetches a known-good kernel (`vmlinux-5.10.223`) and a small rootfs. That rootfs is the "test image" below, not the production one.

## Base image and guest agent

A sandbox rootfs needs the guest agent (`sandkiln-agent`) baked in and running as a systemd service. Without it a sandbox boots but never responds to `exec`, `read-file` or `write-file`: every call times out retrying a vsock connection nothing is listening on. This applies to **every rootfs you use**, and nothing stops you from booting a sandbox from an image that is missing it.

```bash
scripts/dev.sh inject-agent [rootfs-path]
```

This does both steps below in one command: build for the musl target, then inject into `rootfs-path`. The path defaults to `SANDKILN_BASE_ROOTFS` if set, else the daemon's default `~/sandkiln-tools/images/ubuntu-22.04.ext4`. It still needs `sudo` interactively for the injection half, but it removes the most common mistake here: injecting into a different `.ext4` file than the one the daemon is configured to boot from.

The two steps separately. First build the agent for the guest's target:

```bash
cargo build --release -p sandkiln-guest-agent --target x86_64-unknown-linux-musl
```

Then pick one of two rootfs paths and inject into it.

### Quick test path

The small rootfs `fetch-test-image.sh` downloaded is about 300MiB. It proves the whole setup end to end, but it has no `ca-certificates`, Node.js, Python or most common tooling. **Do not use it to back real workloads.**

```bash
images/inject-agent.sh \
  core/target/x86_64-unknown-linux-musl/release/sandkiln-agent \
  ~/sandkiln-tools/images/ubuntu-22.04.ext4
```

`inject-agent.sh` needs `sudo` because it loop-mounts the image. `scripts/dev.sh inject-agent` with no arguments does the same, since that is its default path.

### Production path

Build a real rootfs from scratch: current Ubuntu LTS, current Node.js LTS, Python 3, common CLI tooling, a working systemd init, and the [multi-agent isolation](/self-hosting/operations#security-posture) users, all in one image.

```bash
sudo images/build-universal-image.sh ~/sandkiln-tools/images/universal.ext4
```

It needs `sudo` (debootstrap, loop-mounting, chroot) and several GiB of free disk during the build, 6GiB by default. Pass a size argument to change it; the script header lists every argument and environment override. `setup-multi-agent-users.sh` runs automatically as its last step. Then inject the agent, as in the quick path:

```bash
images/inject-agent.sh \
  core/target/x86_64-unknown-linux-musl/release/sandkiln-agent \
  ~/sandkiln-tools/images/universal.ext4
# or: scripts/dev.sh inject-agent ~/sandkiln-tools/images/universal.ext4
```

If the build fails on an unknown Ubuntu codename or a full disk, see [Troubleshooting](/self-hosting/troubleshooting).

### Point the daemon at the image you built

**This step is easy to skip, and the daemon will not tell you if you do.** `base_rootfs` (`SANDKILN_BASE_ROOTFS`) defaults to `~/sandkiln-tools/images/ubuntu-22.04.ext4`, the quick test image's path, for local development convenience. If you built the production image, set `base_rootfs` to it explicitly (see [Configuration](/self-hosting/configuration)). `scripts/preflight-check.sh` warns if it looks like the small test image, and `sudo -E scripts/preflight-check.sh --root-checks` verifies the agent is actually baked into whatever image is configured. Run it before starting the daemon for real.

Every sandbox create clones the base rootfs (`cp --reflink=auto`). On XFS or Btrfs that is an instant, disk-space-free clone; on ext4 it silently falls back to a full-size copy every time. See [Faster creates](/getting-started/self-hosting#faster-creates-reflink-rootfs-clones) for the setup and measured difference. `preflight-check.sh` reports which filesystem your configured rootfs storage is on.

## Remote storage mounts (optional)

Skip this section unless you want sandboxes to mount an S3-compatible bucket into their own filesystem (`POST /sandboxes/:id/mounts`, see [Remote storage](/concepts/remote-storage) and [FUSE and rclone mounts](/internals/fuse-rclone-mounts)). It needs two things neither rootfs path above provides.

**A guest kernel built with `CONFIG_FUSE_FS`.** Firecracker's default and CI kernel builds, including the one `images/fetch-test-image.sh` downloads, do not enable FUSE, and guest kernels cannot load modules at runtime, so it must be compiled in.

```bash
sudo apt-get install -y build-essential flex bison libelf-dev bc
images/build-guest-kernel.sh 5.10.223 ~/sandkiln-tools/images/vmlinux-5.10.223-fuse
```

This takes a few minutes. Point the daemon at the result with `kernel_path` (`SANDKILN_KERNEL_PATH=~/sandkiln-tools/images/vmlinux-5.10.223-fuse`). That fully replaces the default kernel for every sandbox, not just ones that use mounts, so once you have built it there is no reason not to use it always.

**`rclone` and `fusermount3` baked into the rootfs**, the same way the guest agent is: a static binary injection rather than an apt package, since `rclone mount` is what talks to the bucket from inside the guest.

```bash
scripts/dev.sh inject-rclone <path-to-a-static-rclone-binary> [rootfs-path]
```

Download a static `rclone` build for your architecture first; `rootfs-path` defaults the same way `inject-agent` does. `fusermount3` comes from this host's own `/bin/fusermount3` (install the `fuse3` package here if it is missing). The header comment of `images/inject-rclone.sh` explains why rclone needs it even though the guest agent runs as root.

## Custom images

`base_rootfs` is the daemon-wide default every sandbox boots from unless told otherwise, but a caller can register additional images and pick one per sandbox:

```bash
kiln image create python-3.12-custom ~/sandkiln-tools/images/python-3.12-custom.ext4
kiln sandbox create --image python-3.12-custom
```

Equivalently, `POST /images` with `{"id": ..., "path": ...}`, then `POST /sandboxes` with `{"image_id": ...}`. See [Images](/concepts/images), [Custom image](/guides/custom-image) and [Images: the mechanism](/internals/images).

`path` must already be an ext4 rootfs file staged on the host the daemon process runs on. This does **not** accept an upload and does **not** convert a Docker or OCI image into a bootable rootfs; both are separate, larger problems that are not attempted. The file is copied, not referenced in place, into a managed directory (`images_dir`, `SANDKILN_IMAGES_DIR`), so editing or deleting the original afterward is safe.

**The daemon cannot verify the guest agent is baked into a registered image.** The loop-mount-and-inspect check that `--root-checks` does for `base_rootfs` needs real root, which the daemon deliberately does not have (see [Capabilities](#capabilities)). Every `POST /images` and `GET /images` response says so explicitly (`guest_agent_verified: false`), and `kiln image create` prints a warning to stderr. Run the check against the candidate file yourself before registering it:

```bash
sudo -E scripts/preflight-check.sh --root-checks --rootfs-image ~/sandkiln-tools/images/python-3.12-custom.ext4
```

`DELETE /images/:id` (`kiln image rm <id>`) refuses while any live sandbox, in-flight boot or held snapshot still references the image, the same "cannot delete what is in use" rule `DELETE /drives/:id` enforces.

## Networking

The daemon manages its own bridge network at startup; you do not create the bridge. What you create, once and as root, is a pool of persistent tap devices for the daemon to lease from:

```bash
sudo scripts/host-setup/create-tap-pool.sh 32 $(whoami) sktap
```

This creates `sktap0` to `sktap31` owned by your user. `32` is the concurrent-sandbox-with-networking ceiling for this host. To raise it, re-run the script with the new count and set `tap_pool_size` (`SANDKILN_TAP_POOL_SIZE`) to match. Keep the two in sync; `preflight-check.sh` checks this.

**Why a pre-created pool.** Creating a new tap device is a `TUNSETIFF` ioctl on `/dev/net/tun`, which needs real root. The netlink operations the daemon performs at runtime (attach or detach a tap to the bridge, bring it up or down) work under its ambient `CAP_NET_ADMIN` and do not. Pre-creating the pool once as root sidesteps the problem: from then on the daemon only attaches and detaches existing devices. Mechanism: [TAP devices and bridge networking](/internals/tap-bridge-networking).

**Guest DNS** needs a forwarder, since guests cannot necessarily reach public resolvers directly but can reach the host's own resolver. `scripts/setup.sh` installs it as the `sandkiln-dnsmasq` systemd service, which survives reboots. By hand:

```bash
sudo scripts/host-setup/start-dns-proxy.sh 172.16.0.1   # match bridge_gateway (SANDKILN_BRIDGE_GATEWAY)
```

`scripts/dev-tools/setup-tap-network.sh` is a **different, older tool**: a point-to-point (single tap, no bridge) model used only by `scripts/dev-tools/boot-test-vm.sh` for manual boot testing outside the daemon. It has nothing to do with the daemon's bridged-pool model. Do not run it as part of a normal setup.

## Capabilities

The daemon needs `CAP_NET_ADMIN` to manage tap attachment, the bridge and iptables rules, but runs as an **unprivileged user**, not root. This is deliberate: running the whole HTTP-facing daemon as root would make every bug in it a root-level bug, whereas ambient `CAP_NET_ADMIN` gives it exactly the one privilege it needs. Two ways to grant it, depending on how you run the daemon:

- **Direct `./sandkilnd` invocation:**
  ```bash
  sudo scripts/host-setup/grant-net-admin.sh core/target/release/sandkilnd
  ```
  This sets a file capability on the binary. **It does not survive a rebuild.** `cargo build --release` produces a new binary with no capability, so repeat it after every rebuild or every network operation fails with "Operation not permitted". `sandkilnd-ctl.sh` does this for you.
- **Under systemd (recommended for anything persistent, see [Operations](/self-hosting/operations#running-under-systemd)):** the provided unit grants `CAP_NET_ADMIN` through systemd's `AmbientCapabilities=` at every service start, independent of whatever is `setcap`'d on the binary. A rebuild needs no extra step.

Either way, the daemon's own startup code (`raise_net_admin_ambient` in `core/crates/daemon/src/main.rs`) still runs. It raises whatever is in the process's Permitted set, from either mechanism, into the Inheritable and Ambient sets, so child processes it shells out to (`ip`, `iptables`) inherit the capability too.
