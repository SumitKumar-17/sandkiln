There is no hosted sandkiln service. Every instance is self-hosted: you build the daemon, prepare a kernel and rootfs image, wire up host networking and run `sandkilnd` yourself. This page is the shortest tested path from a bare Linux host to a working daemon creating real, isolated microVM sandboxes. Everything here corresponds to a real script, binary or setting in this repository.

The detail lives in [manual host setup](/self-hosting/manual-setup) (what each step does, for customizing or debugging), [jailer setup](/self-hosting/jailer), [configuration](/self-hosting/configuration), [operations and security](/self-hosting/operations) and [troubleshooting](/self-hosting/troubleshooting). The tooling that checks or automates the steps is `scripts/setup.sh`, `scripts/preflight-check.sh`, `scripts/sandkilnd-ctl.sh` and `scripts/install-systemd-service.sh`.

## Requirements

- Linux x86_64 with `/dev/kvm` readable and writable by your user (check with `ls -la /dev/kvm`). Bare metal and nested virtualization both work. If you are not in the owning group: `sudo usermod -aG kvm $USER`, then log in again. Nothing is verified for aarch64.
- `sudo`, for one-time host setup only. The daemon never runs as root; it holds only `CAP_NET_ADMIN`. See [TAP devices and bridge networking](/internals/tap-bridge-networking).
- Rust via [rustup](https://rustup.rs), and `dnsmasq-base` for the guest DNS forwarder. `scripts/setup.sh` adds the musl target (`rustup target add x86_64-unknown-linux-musl`) and installs `musl-tools` with `apt` if missing. Node.js 20+ is needed only to build the CLI or SDK from source. The full prerequisite list is in [Manual host setup](/self-hosting/manual-setup#prerequisites).

`scripts/preflight-check.sh` reports what is missing, using the same `SANDKILN_*` variables and defaults as the daemon, so it tells you what is missing before you try to start anything.

## Setup and start

```bash
git clone https://github.com/SumitKumar-17/sandkiln.git
cd sandkiln
scripts/setup.sh
scripts/sandkilnd-ctl.sh start
```

`setup.sh` is idempotent. It builds the workspace and the guest agent, installs Firecracker and the jailer into `~/sandkiln-tools/bin`, fetches a test kernel and rootfs, injects the agent, creates the tap device pool, installs the guest DNS forwarder as the `sandkiln-dnsmasq` systemd service (it survives reboots), and grants the daemon `CAP_NET_ADMIN`. It writes `sandkiln.toml` at the repo root (only if absent, so a hand-edited file is never overwritten), which `sandkilnd-ctl.sh` passes to the daemon, so `start` needs no environment variables. `start` validates the config with `sandkilnd --check-config`, runs preflight, builds if needed, and returns only after `/healthz` answers. The steps `setup.sh` runs, one at a time, are in [Manual host setup](/self-hosting/manual-setup).

That is a real, working daemon, enough to prove the whole stack end to end, but it boots from Firecracker's small CI test image: about 300MiB with no language runtime or `ca-certificates`. For a real Ubuntu base image with current Node.js and Python (needs `sudo`, about 8GiB of free disk, several minutes):

```bash
scripts/setup.sh --production
```

Other daemon commands (`status`, `logs [-f]`, `restart`, `stop`, and running under systemd) are in [Operations](/self-hosting/operations).

## Verify

```bash
curl http://127.0.0.1:7777/healthz
# ok
curl -s -X POST http://127.0.0.1:7777/sandboxes -d '{}'
# {"id":"..."}
curl -s -X POST http://127.0.0.1:7777/sandboxes/<id>/exec \
  -H 'Content-Type: application/json' \
  -d '{"command":"echo","args":["hello from a real microVM"]}'
curl -X DELETE http://127.0.0.1:7777/sandboxes/<id>
```

If you set an auth token, add `-H "Authorization: Bearer $SANDKILN_AUTH_TOKEN"` to the sandbox calls. For full coverage, run `scripts/integration-test.sh` ([Operations](/self-hosting/operations#automated-verification-and-clients)).

Then continue with [JS/TS](/getting-started/js), [Python](/getting-started/python) or the [CLI](/getting-started/cli).

## Configuration

`sandkilnd` reads `SANDKILN_<KEY>` environment variables, then `sandkiln.toml`, then built-in defaults. `setup.sh` writes a starter file and `sandkilnd-ctl.sh start` passes it to the daemon. Resolution order, the `--check-config`, `--print-config` and `--config-reference` flags, and every setting are in [Configuration](/self-hosting/configuration).

## Before exposing it beyond localhost

With no `auth_token`, every route except `/healthz` and `/metrics` is open: anyone who can reach the port can create sandboxes, read and write files inside them, and delete persistent drives. The daemon logs a warning at startup so this is never silent. Set a token in `sandkiln.toml` (`auth_token = "..."`, with `chmod 600`) or from the environment:

```bash
SANDKILN_AUTH_TOKEN=$(openssl rand -hex 32) scripts/sandkilnd-ctl.sh restart
```

Clients send it as `Authorization: Bearer <token>` and a mismatched, missing or malformed header gets `401`; see [Auth](/concepts/auth). The daemon compares it in constant time (`core/crates/daemon/src/auth.rs`). It is one shared secret, with no per-caller scoping; see the [security posture](/self-hosting/operations#security-posture).

## Stopping the daemon

`sandkilnd-ctl.sh stop` (or `SIGTERM`) drains in-flight requests and snapshots every live sandbox before exiting. Details, timings and crash cleanup are in [Operations](/self-hosting/operations#stopping).

## Faster creates: reflink rootfs clones

Each sandbox gets a private copy of the base rootfs. If `SANDKILN_ROOTFS_DIR` is on the same reflink-capable filesystem (XFS with `reflink=1`, or Btrfs) as `SANDKILN_BASE_ROOTFS`, the copy is a copy-on-write clone: a cold create measured 17.9ms instead of 187.5ms. On an ext4-only host:

```bash
sudo scripts/host-setup/create-reflink-volume.sh "$USER" 20
```

It mounts the volume (default `/mnt/sandkiln-xfs`), creates `<mountpoint>/rootfs` and hands ownership to that user. Copy your base image onto the same mount (the base image and the clone directory must share the filesystem), then set `base_rootfs = "<mountpoint>/<image>.ext4"` and `rootfs_dir = "<mountpoint>/rootfs"` in `sandkiln.toml` (or the env vars `SANDKILN_BASE_ROOTFS` and `SANDKILN_ROOTFS_DIR`). Check `rootfs_clone_total{method="reflink"}` on `/metrics`; a rising `method="copy"` means the two paths are on different filesystems. The loop mount does not survive a reboot; re-run the script to remount. `preflight-check.sh` reports which filesystem your configured rootfs storage is on. Without reflinks the disk cost is a full rootfs copy per sandbox; with them, per-sandbox storage growth is nil. See [Startup latency](/architecture/startup-latency).

## Optional: remote storage mounts

Mounting an S3-compatible bucket needs a guest kernel built with `CONFIG_FUSE_FS` and `rclone` plus `fusermount3` in the rootfs. Neither is set up by default. See [Remote storage mounts](/concepts/remote-storage) and [Manual host setup](/self-hosting/manual-setup#remote-storage-mounts-optional).
