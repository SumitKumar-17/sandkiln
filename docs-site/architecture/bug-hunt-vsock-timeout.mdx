---
title: "The vsock timeout that could hang a stop"
description: Why every host-to-guest vsock call carries a 3-second read and write timeout.
---

**Claim:** before the vsock client had I/O timeouts, pausing a VM and then stopping it hung forever. Every call now has a 3-second bound, set once at the transport.

## What was wrong

`Vm::stop` sends `exec sync` to the guest agent before killing Firecracker, so unflushed writes to an attached drive are not lost. Snapshots changed the precondition: Firecracker requires a VM to be paused before it takes a snapshot, and a paused VM's vCPUs are halted, so the guest agent cannot answer anything, including that `sync`.

The vsock client set no read or write timeout. A single blocked `read` therefore never returned. The 5-second deadline in the retry loop above it did not help, because it bounds the gap between connection attempts, not an attempt already in progress. Found by running a full snapshot-then-stop cycle: pause, stop, hang, every time.

## What changed

`core/crates/vmm/src/vsock_client.rs` sets `IO_TIMEOUT` (3 seconds) as both read and write timeout on every stream it opens. It is applied unconditionally rather than special-cased for the snapshot path, so any unresponsive guest (paused, crash-looped, kernel-panicked) and any future caller gets the same bounded worst case. Streaming calls (PTY, streamed exec) clear the read timeout after the handshake, since they legitimately idle.

## What to do differently

- Put timeouts at the transport layer, not in each caller.
- Treat "the guest may be paused or dead" as a normal state when adding any host-to-guest call, and give it a failure path. For a VM already known dead, use `Vm::force_stop` rather than `Vm::stop` so the pre-kill `sync` does not cost a second timeout.
